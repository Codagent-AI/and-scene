# Create And Scene implementation checklist

| ID | Behavior | Spec reference | How to verify |
|---|---|---|---|
| I-1 | The skill asks for missing topic, style, step content, and visual descriptions one question at a time. Complete prompts can go straight to building. The user may opt in to building with partial detail and iterate. ASCII mockups are optional for key or complex steps. | `specs/presentation-skill/spec.md` § Interactive requirement gathering | Inspect the skill procedure for the missing-detail, complete-prompt, and partial-detail branches, including when optional mockups are offered. |
| I-2 | Before creation or modification, the skill detects the build setup, scene kit, and presentation index by contract, tolerating cosmetic differences. It adds all anchors when none exist, adds only missing anchors and their dependencies for a partial scaffold, and reuses a complete scaffold. Dependency installation precedes creation where scaffolding is needed. | `specs/presentation-skill/spec.md` § Self-bootstrapping scaffold | Inspect the skill's anchor-detection and scaffold procedure for all three cases, preservation of existing anchors, and dependency-install ordering. |
| I-3 | A standalone scaffold goes at the root and a monorepo scaffold goes into a self-contained `presentations/` app. The skill states its target and obtains confirmation before writing scaffolding in the specified non-empty project case. | `specs/presentation-skill/spec.md` § Self-bootstrapping scaffold | Inspect the skill's target resolution, reuse of an existing presentation app, and confirmation gate before writes. |
| I-4 | Bootstrap and per-presentation templates resolve from the skill directory. A standalone materialized bootstrap has all three anchors, the full runtime, build, lint, and browser dependency set and committed lock data, and can build and smoke-render its registered route outside the source checkout. | `specs/presentation-skill/spec.md` § Self-bootstrapping scaffold | Inspect relative path instructions and both template locations. Run `INT-001` from an isolated location outside the source checkout, including the dependency, build, and route smoke checks. |
| I-5 | The bootstrap works without a styling framework and supplies no presentation colors, fonts, spacing scale, card or button treatments, borders, shadows, or theme tokens. Its scene-kit files and verification and inspection scripts stay aligned with the repository copies. | `specs/presentation-skill/spec.md` § Self-bootstrapping scaffold; `specs/evolving-scene-presentations/spec.md` § Style ownership boundary; `design.md` § Decisions | Use `INT-001` for the materialized style-neutral build, dependency and configuration checks, and byte comparison of kit files. Compare the root and bootstrap verification and inspection scripts byte for byte. |
| I-6 | A new presentation is created in its own directory with local scene entities and steps and is added to the registry at its own route. Existing files and entries are preserved. | `specs/presentation-skill/spec.md` § Create a new presentation | Inspect the skill procedure and presentation templates for local files and additive registration. Use a router component test with several entries to confirm each remains independently reachable. |
| I-7 | The root landing page lists registered presentations, matched slugs lazy-load their own entry, and unknown paths have a fallback. Registration uses an explicit array. | `specs/presentation-skill/spec.md` § Create a new presentation; `design.md` § Routing + registry | Inspect the registry and lazy loader. Use a router component test for landing links, selected loader and route, and a fallback on an unmatched pathname. |
| I-8 | Presentation visuals are owned by the presentation or host. Plain CSS is the default, with existing host frameworks or a user-requested framework allowed. | `specs/presentation-skill/spec.md` §§ Create a new presentation, Generated presentation quality bar | Inspect the skill's styling instructions, authoring templates, and sample CSS ownership. |
| I-9 | An ambiguous modification request lists existing presentations and resolves the target before edits. Once identified, the skill asks only about the requested change and limits edits to the selected presentation's requested steps, entities, or style. | `specs/presentation-skill/spec.md` § Modify an existing presentation | Inspect the modification procedure for target resolution before writes and a scoped path that bypasses the full creation interview. |
| I-10 | Before reporting success on creation or modification, the skill builds, renders at least the first step without runtime or console errors, and checks browser composition at the first, last, and dense or key steps, including a narrow viewport when responsive-sensitive. It repairs failures and reruns the affected checks. | `specs/presentation-skill/spec.md` § Self-verify before reporting completion | Inspect the skill procedure for the build, route-specific render, and screenshot review gates and the repair-and-recheck loop. |
| I-11 | Generated work follows the evolving-scene model with a caption per step and next/previous navigation. The visual review requires important content to fit the fixed canvas, intentional overlaps to remain readable, and scene content to clear the chrome. | `specs/presentation-skill/spec.md` § Generated presentation quality bar | Inspect the skill procedure and authoring templates for these requirements. Use component tests for caption updates, next/previous controls, and the fixed canvas contract. |
| I-12 | Inspection uses the project-local screenshot helper when available, or a temporary Playwright helper under the project root otherwise. The skill reviews flagged steps, fixes unintended collisions and weak chrome styling, and marks only readable intentional overlaps. | `specs/presentation-skill/spec.md` §§ Self-verify before reporting completion, Generated presentation quality bar | Inspect the skill's helper preference and fallback location, warning review criteria, overlap marking, and reinspection instructions. |
| I-13 | Each ordered step has a stable ID, era, presenter title, browse caption, and active diagram state. On-screen numbering follows array order after insertion, removal, or reordering. Typed scene payloads reach `Presentation` without casts. | `specs/evolving-scene-presentations/spec.md` § Scene step model | Run a component test with changed step order and content. Type-check a strongly typed grouped-step fixture with a cast-free presentation call. |
| I-14 | Continuing entities retain their identity and animate changes in position, size, label, and emphasis. New entities enter after continuing motion settles. Departing entities animate out. | `specs/evolving-scene-presentations/spec.md` § Stable entities morph across steps | Use component tests with Motion instrumentation to check stable projection IDs, updated state, entrance scheduling against layout timing, and exit presence on removal. Inspect how the primitives wire Motion to those transitions. |
| I-15 | Adjacent steps sharing a group key and scene component update the same scene instance and its payload. Continuing entities avoid newcomer fades, and the composition can preserve intentional stacking and overlap. | `specs/evolving-scene-presentations/spec.md` § Persistent grouped scenes | Use a component fixture that observes scene and entity instance identity, payload updates, newcomer-animation assignment, and stacked geometry across grouped steps. Inspect the keyed presence boundary for distinct scenes. |
| I-16 | Generic primitives and chrome expose stable `data-presentation-*` styling hooks and accept author-provided class or style where relevant. Literal coordinates and raw Motion elements with stable layout IDs are supported. The kit supplies behavior and geometry without default presentation treatments or framework dependencies. | `specs/evolving-scene-presentations/spec.md` § Style ownership boundary; `design.md` § Scene kit (the engine) | Use a component contract test for hooks and coordinate/style pass-through. Inspect primitive styles and dependencies for visual neutrality, and the authoring template for composition with raw Motion elements. |
| I-17 | The kit shows a bottom-right `made by and-scene` link to the and-scene GitHub repository with a stable styling hook. Top-left branding appears only when supplied by the host. | `specs/evolving-scene-presentations/spec.md` § Kit attribution | Use a component test for default text, destination, hook, and the header with and without explicit branding. Inspect the attribution placement rules. |
| I-18 | The configured initial mode opens correctly. Present mode shows the active marker and one-line title with browse chrome hidden. Browse mode shows the active title, multi-line caption, wide-viewport table of contents, progress indicators, and prev/next controls. Toggling with P keeps the step index. | `specs/evolving-scene-presentations/spec.md` § Present and browse modes; `design.md` § Scene kit (the engine) | Use a component test for each initial mode, rendered chrome, and toggling at a middle step. Inspect the responsive rule for the table of contents and the title/caption layout rules. |
| I-19 | Right, Space, and PageDown advance. Left and PageUp go back. Horizontal swipes move one step in the intended direction. Focused interactive controls retain their own key handling. Prev/next controls work, and navigation clamps at both ends. | `specs/evolving-scene-presentations/spec.md` §§ Step navigation, Boundary behavior | Use hook/component tests for key mappings, focused-control events, swipe directions, button actions, and attempted movement at each boundary. |
| I-20 | A progress indicator jumps to its step and a table-of-contents entry jumps to the first step of its era. Semantic current-state attributes and active styling hooks update on both controls. | `specs/evolving-scene-presentations/spec.md` § Step navigation | Use a component test with multiple steps per era and multiple eras. Check targets, index, semantic state, and active hooks after each kind of jump. |
| I-21 | The default canvas is 880 × 380. Fit scaling uses each mode's available geometry and a uniform scale on resize with fixed internal coordinates. Step changes at fixed viewport and mode do not affect scale. | `specs/evolving-scene-presentations/spec.md` § Fixed-canvas fit scaling; `design.md` § Scene kit (the engine) | Use scaling and stage tests for wide and narrow sizes, both modes, default and overridden dimensions, and fixed inner geometry across steps and resize. |
| I-22 | The canonical sample accumulates the conversation row, prompt, skill/question exchange, and step-card tray. Cards show title, caption, and visual, with morphs indicated on links between cards. The next beats keep existing geometry, add the dashed ghost card and depth control, dock the scene-kit socket beneath the unframed tray, and chain verification with build/render and a green pass check in the tray row. The edit arc flags the edited card and the final labeled frame encloses the whole diagram as a self-reference. | `specs/presentation-verification/spec.md` § Committed reference sample, normative nine-step table | Inspect sample state, stable IDs, layer positions, links, and local CSS against each scene-intent entry in the table, including accumulated entity identity and fixed placement through the closing frame. |
| I-23 | Sample-owned CSS makes active progress and table-of-contents states distinguishable, presents legible attribution, and preserves readable intentional overlaps with narrowly scoped markers. | `specs/presentation-skill/spec.md` § Generated presentation quality bar; `specs/presentation-verification/spec.md` § Visual inspection artifacts | Inspect the sample style rules, active hooks, attribution sizes, positioning against the canvas and chrome, breakpoint rules, and any allow-overlap markers against the marked elements. |
| I-24 | The root verification command builds the whole application, including all presentations and the index. It finds the registered sample, checks its name and all nine normative titles and captions in order, and reaches every step cleanly in production Chromium through the public count/index hooks. Preview host, readiness probe, and browser URL use `127.0.0.1`, and success is explicit with exit zero. | `specs/presentation-verification/spec.md` §§ Build verification, Committed reference sample, Render verification, Pass/fail reporting | Run `E2E-001` through `npm run verify`. Assert the built sample route and all observed indices and compare titles and captions to the normative table. Inspect preview/probe/navigation addresses if they are not exposed in command output. |
| I-25 | Verification fails clearly and exits non-zero on a build failure, a missing or malformed reference sample, a console or uncaught page error, or a step that fails to advance. Output identifies the failing phase and the offending step for render or transition faults. Preview subprocesses are cleaned up on failure. | `specs/presentation-verification/spec.md` §§ Build verification, Committed reference sample, Render verification, Pass/fail reporting; `test-plan.md` § End-to-End Tests | Run `E2E-002` in disposable fault fixtures and assert exit status, phase and step diagnostics, absence of a success result, and process cleanup. Cover both browser error channels in isolated handler tests if the fault fixture exercises only one. |
| I-26 | The project-local inspection helper opens a registered route in Chromium on a production preview, waits for the configured transition settle interval, and writes one screenshot per step at a standard desktop viewport in a predictable project-local directory. | `specs/presentation-verification/spec.md` § Visual inspection artifacts | Run `INT-002` using its controlled multi-step presentation. Assert output paths, screenshot count and viewport dimensions, and capture timing after each transition. |
| I-27 | Inspection warns with step and element details for unmarked visible text/chrome collisions, skips overlaps inside marked subtrees, identifies indistinct active progress or table-of-contents chrome, and points to the attribution hook for missing, undersized, or browser-default attribution. Findings are advisory. | `specs/presentation-verification/spec.md` § Visual inspection artifacts; `design.md` § Verification | Use the same `INT-002` fixture run to assert step-specific warnings, the marked-overlap exemption, and successful capture despite warnings. Use diagnostic unit tests for additional visibility, active-control, and attribution variants. |
| I-28 | The installed dependency set supports the fast unit and contract suite, lint, and the TypeScript production build. Browser-backed test runs are separate. Generated build output, dependencies, and inspection screenshots stay out of the committed change. | `test-plan.md` § Coverage Strategy; `design.md` § Verification; repository verification instructions | Check install from lock data with `npm ci`, run `npm test`, `npm run lint`, and `npm run build` within the applicable test limits, and inspect npm script separation and tracked paths. |
