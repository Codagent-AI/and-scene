# Presentation

## Overview

A presentation generated by this skill is one evolving diagrammatic scene:
stable entities (boxes, labels, arrows, groups) that move, morph, and
accumulate through an ordered sequence of named steps, not a deck of
independent slides. Every presentation is a self-contained, routed React app
built on the reusable **scene kit** at `src/presentation-kit/` (or
`presentations/src/presentation-kit/` in a monorepo target — see
[Resolve the target](#2-resolve-the-target-and-scaffold-if-needed)).

This document is the procedure. `templates/bootstrap/` is a full snapshot of
the app shell + scene kit used only when scaffolding a fresh project;
`templates/presentation/` is the pattern for one presentation folder. Resolve
every template path relative to this file's own directory
(`skills/presentation/`), never relative to the caller's working directory,
so the skill behaves the same regardless of where it is invoked from.

## Procedure

### 1. Gather requirements

Ask one question at a time. Do not assume anything the user can still tell
you, and do not block on completeness — the user may choose to build from
partial detail at any point.

Cover, in this rough order, skipping anything already given in the prompt:

1. **Topic** — what is this presentation about, and (if not obvious) who is
   the audience?
2. **Visual style** — palette, tone, and any reference presentation or brand
   to match. Plain CSS is the default; only reach for a styling framework if
   the host project already uses one or the user asks for it.
3. **Per-step content and visual intent** — for each step: what changes on
   screen (entities entering, moving, connecting, or being emphasized) and
   what the caption says. Confirm whether this is a new presentation or a
   modification (see [Create vs. modify](#3-create-a-new-presentation-or-modify-an-existing-one)).

At any point, if a step's layout is key to understanding the presentation or
is visually complex (many entities, non-obvious arrangement), you may sketch
an ASCII mockup of that step's canvas and ask the user to confirm it before
building. Do this selectively — not for every step — and only when it
resolves real ambiguity.

If the user says to proceed before every question is answered, build from
what you have and note the assumptions you made in the completion summary.

### 2. Resolve the target and scaffold if needed

**Detect the three contract anchors** at the contract level (their presence,
not a byte-identical match — file naming or extra dependencies don't matter):

1. **Build setup** — a Vite + React + TypeScript app with a working
   `npm run build` (look for `vite.config.ts`, a React + TypeScript
   `package.json`, and a `tsconfig.json` that builds).
2. **Scene kit** — a `presentation-kit/` (or equivalently named) module
   exporting the `Step`/`Scene` contract, a stage/host that mounts the active
   step and runs entity morphs, present/browse navigation, and chrome
   (captions, table of contents, progress, attribution).
3. **Presentation index** — a registry file mapping presentation slugs to
   routes (an explicit array, not auto-discovery).

**Resolve where the app belongs:**

- **Empty directory or standalone (non-monorepo) project** — the target is
  the repository root.
- **Monorepo** (a `package.json` with a `workspaces` field, a
  `pnpm-workspace.yaml`, or a `packages/`/`apps/` layout) — the target is a
  self-contained `presentations/` app, not the monorepo root.
- **Already inside a presentation app** (all three anchors present at the
  current location) — use it as-is.

**Scaffold only what's missing:**

- All three anchors present → skip scaffolding, go to step 3.
- Some anchors present → copy only the missing pieces from
  `templates/bootstrap/` (e.g. add `src/presentation-kit/` without touching an
  existing router or registry), so anchors already present are left
  untouched.
- No anchors present (empty or fully unscaffolded target) → copy the whole of
  `templates/bootstrap/` into the target: `package.json`, `vite.config.ts`,
  the `tsconfig*.json` files, `eslint.config.js`, `index.html`, `public/`,
  `.gitignore`, `src/` (including `src/presentation-kit/`,
  `src/presentations/index.ts` as an empty registry, `src/main.tsx`,
  `src/Root.tsx`, `src/router.ts`, `src/Landing.tsx`, `src/index.css`), and
  the whole `scripts/` directory (the `verify.mjs` and
  `inspect-presentation.mjs` entry points import sibling modules from it, so
  copying only those two leaves a broken scaffold). Merge into an
  existing `package.json`/`.gitignore` instead of overwriting when the target
  already has one of those files but was missing an anchor.
- **Non-empty project missing scaffolding** — before writing anything, state
  the resolved target location (root vs. `presentations/`) and what will be
  scaffolded, and wait for the user to confirm.

**Install dependencies** whenever scaffolding adds or touches
`package.json` — do not assume any are already installed. The required set:
`react`, `react-dom`, `motion`, `lucide-react` (runtime); `vite`,
`@vitejs/plugin-react`, `typescript`, `@types/react`, `@types/react-dom`,
`@types/node`, the ESLint stack (`eslint`, `@eslint/js`, `typescript-eslint`,
`eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`, `globals`), and
`playwright` (for the render/screenshot checks). Run `npm ci` if a lockfile
exists in the target, otherwise `npm install`. **Do not add Tailwind or any
other styling framework** unless the host project already depends on one or
the user explicitly asked for it — the scaffold and the scene kit stay
styling-framework-neutral, with zero default colors, fonts, spacing, borders,
shadows, card/button treatments, or theme tokens.

### 3. Create a new presentation, or modify an existing one

**If the request doesn't clearly name an existing presentation to change**,
treat it as creating a new one. **If it asks to change a presentation but
doesn't clearly identify which one** (or the named one doesn't exist), list
the presentations currently in the registry and ask which to modify before
changing anything.

#### Creating a new presentation

1. Pick a URL-safe `slug` (kebab-case) from the topic; confirm it doesn't
   already exist in the registry.
2. Copy `templates/presentation/` into `src/presentations/<slug>/` (or the
   monorepo target's equivalent path), then replace every `__SLUG__` and
   `__TITLE__` placeholder and the example content:
   - `entities.ts` — one stable `layoutId` string per entity that should
     morph (not remount) across steps, namespaced with the slug so it can't
     collide with another presentation.
   - `steps/payload.ts` — replace the placeholder index signature with a
     concrete `Payload` interface covering every field any step's `Scene`
     needs, so the whole presentation stays typed without casts.
   - `steps/*.tsx` — one file per step (or per small group of steps),
     composing `Box`/`Label`/`Arrow`/`Frame`/`Emphasis`/`SymbolChip` from the
     scene kit. Steps that should persist on screen and only change data
     (not remount and cross-fade) share a `groupKey` and `Scene` component.
     Wrap newcomer entities in `Appear` so they animate in only after
     persisting entities finish their layout morph; wrap each step's diagram
     in `SceneLayer` so mounting one layer doesn't reflow another.
   - `steps/index.ts` — the ordered `STEPS` array, one entry per step, in
     presentation order.
   - `Talk.tsx` — renders `<Presentation steps={STEPS} title="…" />`; set
     `initialMode="browse"` unless the request calls for present mode by
     default.
   - `style.css` — the presentation's own visual design (plain CSS by
     default). Give the active progress dot, active table-of-contents entry,
     and the attribution link a legible, visually distinct treatment; do not
     add these defaults to the scene kit itself.
3. Register it in `src/presentations/index.ts` by adding one entry —
   `{ slug, title, load: () => import('./<slug>/Talk') }` — to the existing
   array. Leave every other entry untouched so existing presentations remain
   intact and reachable.

#### Modifying an existing presentation

1. Read the target presentation's `entities.ts`, `steps/*`, `Talk.tsx`, and
   styling.
2. Ask only about the specific change requested (new/changed steps, entities,
   or style) — do not re-ask the full topic/style/step gathering flow for
   unrelated parts of the presentation.
3. Scope edits to that presentation's folder and, if needed, its registry
   entry (e.g. a title change). Do not touch other presentations or the scene
   kit's shared behavior/styling contract.

### 4. Self-verify before reporting completion

Before reporting success:

1. **Build** — run `npm run build`; fix any type or build error.
2. **Render check** — at minimum, load the presentation's route and confirm
   its first step renders with no console or runtime errors. If
   `npm run verify` is available and fast enough for the scope of the change,
   prefer it — it also drives every step of every registered presentation
   through a real browser via `scripts/verify.mjs`. Fix any failure and
   re-run rather than reporting success with a red check.
3. **Visual composition check** — capture and review screenshots of the
   first step, the last step, and any dense/key steps; also check a narrow
   viewport if the presentation is responsive-sensitive. Prefer the
   project-local `scripts/inspect-presentation.mjs` helper
   (`npm run inspect -- <slug>`) over an ad hoc script outside the project
   tree, so browser tooling resolves from the project's own dependencies and
   screenshots are captured after animations settle. Review any warnings it
   prints:
   - unmarked overlap between scene content and chrome (caption, table of
     contents, progress, nav, header/attribution) — fix accidental
     collisions; for an overlap that is intentional and still readable, mark
     the scene element `data-presentation-allow-overlap` instead of
     suppressing the warning silently.
   - an active progress dot or table-of-contents entry that isn't visually
     distinct from an inactive one — style it in the presentation's CSS.
   - a missing, browser-default, or undersized attribution link — style
     `[data-presentation-attribution]` in the presentation's CSS (the scene
     kit renders the link itself; the presentation and host only style it).
4. Only report completion once build, render check, and visual composition
   check all pass.
