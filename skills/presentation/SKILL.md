# Presentation

Resolve every resource below relative to this SKILL.md directory, never the caller's working directory. The bootstrap is `templates/bootstrap/`; starter presentation files are `templates/presentation/`. Use the hybrid procedure and real scene kit rather than making a disconnected slide deck.

1. Gather the topic, visual style, and each step's content and visual description, one question at a time. Do not invent details the user can still provide. Ask what persists, moves, enters, or exits between beats. The user controls depth: explicitly choosing to build with partial detail is enough; do not impose a completeness gate. A complete initial request needs no further questions. Optionally show an ASCII mockup for a key or complex composition, without requiring one for every step.
2. Identify create versus modify. For ambiguous modification, list the registry's existing presentations and ask which target before changing files. For an identified target, ask only about requested changes to steps, entities, or style; do not repeat the full create interview. Preserve other presentations and their routes.
3. Resolve scaffold anchors by their contracts: a working Vite/React/TypeScript build; a reusable Step/Scene engine with stage, morphs, navigation, chrome and scaling; and a registry mapping presentations to routes. Cosmetic naming, formatting or extra dependencies do not justify re-scaffolding. Inspect equivalent host files, not just conventional paths. Reuse complete anchors; add only missing anchors and required dependencies without disturbing existing ones.
4. Resolve target: reuse a presentation app already containing the anchors. Otherwise detect monorepos by package.json workspaces, pnpm-workspace.yaml, packages/ or apps/ and create a self-contained `presentations/` app; standalone or empty projects use the root. In any non-empty project missing the kit or registry, state the exact resolved target and obtain user confirmation before writing. Preserve the monorepo root's existing build and unrelated content.
5. The helper `scripts/scaffold.mjs` beside this skill prints a plan by default. Invoke it using an absolute skill-relative path from any working directory. Its conventional-path detection is a convenience only: inspect equivalent anchors first; import `plan(root, {build, kit, index})` for known contract results, and copy only the missing anchor's files if a custom layout needs adaptation. Never run a blind full bootstrap over a partial host. `scaffold(plan, {confirmed:true})` or CLI `--apply --confirmed` is only appropriate after actual confirmation where required. In an empty target use `--apply`. Bootstrap files never overwrite existing files. Merge necessary dependencies/configuration explicitly when an existing host uses different paths.
6. For a fully absent scaffold, copy the bootstrap and install dependencies. Do not assume anything is installed: ensure react, react-dom, motion, lucide-react, vite, @vitejs/plugin-react, typescript, @types/react, @types/react-dom, @types/node, ESLint with its configured plugins/typescript stack, and playwright. Install Chromium with `npx playwright install chromium` when unavailable. No Tailwind, plugin, theme tokens, fonts, colors, spacing scale, borders, shadows, card or button defaults belong in the kit or generic scaffold. Optional frameworks belong to the host only when already used or explicitly requested. The included reference's CSS is an example local to that presentation.
7. Create `src/presentations/<slug>/entities.ts`, `steps/`, and `Talk.tsx` using presentation templates. Register one explicit `{slug,title,load:()=>import('./<slug>/Talk')}` entry without removing existing entries. Each presentation has its own route and entity namespace. The landing page lists the registry. For modifications edit only the identified target and necessary registration or verification artifacts.
8. Define ordered steps with stable id, era, one-line presenter title, paragraph browse caption, Scene, and typed payload. Numbers derive from order. Share Scene and groupKey for successive states of one evolving diagram. Continuing entities retain layoutId and morph in place; wrap only newcomers in delayed Appear, use exits for departures. Use absolute SceneLayer and coordinates when helpful; raw motion elements with stable layoutIds are supported. Preserve intentional readable stacking. The default canvas is 880 × 380, uniformly fitted in browse and present modes.
9. Plain CSS owned by the presentation is the default. Style stable `data-presentation-*` hooks locally: title, caption, navigation, current state, ToC, mode, and attribution. Give `[data-presentation-active="true"]` a visibly distinct treatment. Make `[data-presentation-attribution] a` legible (at least 11px, deliberate color/treatment). Keep the default bottom-right made by and-scene link. Top-left branding is host opt-in. Never move a presentation's visual system into the reusable kit.
10. Before reporting success run `npm run build`, a real-browser render check of the generated/modified route's first step without console.error or pageerror, and the project's full `npm run verify` for the reference. Ensure every generated step has its caption, previous/next navigation, and evolving entities. Fix build/runtime/transition failures and rerun affected checks; a failed check is never success.
11. Run `npm run inspect -- <slug>` using the project-local helper. It captures every settled step from a production preview into artifacts/inspection/<slug> and emits advisory warnings. Prefer this helper to outside scripts so Playwright resolves locally. If absent, place a temporary helper under the project root. Inspect the first, last, dense/key screenshots or equivalent browser views and narrow views for responsive-sensitive work. Check important content fits the fixed canvas, overlaps remain readable, and captions/progress/ToC/navigation do not collide with scene content. Review every referenced warning, fix accidental collisions, indistinct current state, and small/browser-default attribution. Mark only intentional readable overlap subtrees with `data-allow-overlap="true"`; never use that marker to hide accidental collisions. Rebuild, rerender and recapture after fixes. Warnings and images support visual review; neither is an automated visual-quality verdict.
12. Report completion only after build, render, and visual composition checks pass. State the checks and any remaining advisory information accurately.
